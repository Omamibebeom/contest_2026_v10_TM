//==============================================================================
// a_channel_flow.txt —— a 通道 (放置板物件) 在 TM Flow 要拉哪些圖元
//
// a 通道【不用 script】, 全部用 TM Flow 的圖形化指令 (圖元) 組成。
// b 通道 (隨機板物件) 才用 script (tm-flow-v1.txt, 不需修改)。
//
// 本文件所有數字都來自樹莓派端程式, 改程式就要同步改這裡:
//   3-bit 編碼表 / 失敗碼 / 保持秒數  → pi_gpio_controller.py 頂端 IO_CODES、FAIL_CODE、HOLD_SEC、FAIL_HOLD_SEC
//   辨識 (投票) 秒數                    → main_contest.py 的 VOTE_SEC
//   IO["ControlBox"].DO / .DI[n] 語法   → TMscrip_TW 手冊
//   起始姿態與電爪開合一次              → 2025 題目卷「評分規範」(2026 題目卷出來後請再對一次)
//
// a 通道只判斷【顏色】, 不判斷形狀。
//==============================================================================


//===== 賽前接線 (BCM 編號, 見 pi_gpio_controller.py 的 RELAY_PINS / READY_PIN) =====
//   手臂 DO0        ──▶ 樹莓派 GPIO26   (ready: 通知樹莓派開始辨識)
//   樹莓派 R1 (17)  ──▶ 手臂 DI0        (觸發: 編碼有效, 保持 HOLD_SEC = 7 秒)
//   樹莓派 R2 (27)  ──▶ 手臂 DI1        ┐
//   樹莓派 R3 (22)  ──▶ 手臂 DI2        ├ 3-bit 顏色編碼
//   樹莓派 R4 (23)  ──▶ 手臂 DI3        ┘
//   光電感測器      ──▶ 手臂 DI4        (深度, 不經樹莓派; 腳位依現場; 題目沒有深度判斷就不用接)


//===== DI 解碼表 (預設值; 選手若改了 IO_CODES / FAIL_CODE, 這張表要跟著改) =====
//   DI0   DI1 DI2 DI3   意義
//    1     0   0   1    red
//    1     0   1   0    blue
//    1     0   1   1    green
//    0     1   1   1    【辨識失敗】DI0 不會變高, 手臂靠 WaitFor 逾時後讀 DI1~DI3 得知
//    0     0   0   0    待命 / 訊號已收回
//
//   ※ 失敗碼 1 1 1 是 IO_CODES 沒用到的組合, 所以就算 DI0 那條線接觸不良,
//     也不會把某個顏色誤讀成失敗。新增顏色時不要用 1 1 1。


//===== 時序 (以手臂拉高 DO0 = ready 的瞬間為 t = 0) =====
//   樹莓派: t=0 開始投票 VOTE_SEC = 3 秒 (每一幀看到的最大物件顏色投一票)
//   成功: t=3 先擺好 R2 R3 R4 → t=4 R1 拉高 → 保持 HOLD_SEC = 7 秒 → t=11 全部關閉
//   失敗: t=3 R2 R3 R4 = 1 1 1, R1 不拉高 → 保持 FAIL_HOLD_SEC = 10 秒 → t=13 全部關閉
//
//   手臂 WaitFor DI0 的 timeout 設 8000 ms:
//     成功時 t=4 就通過; 失敗時 t=8 逾時, 此時失敗碼還在 (到 t=13), 讀 DI1~DI3 = 1 1 1 即知失敗。
//   不可設 15 秒: 失敗碼 t=13 已收回, 逾時後只讀到全 0, 分不出「失敗」和「樹莓派沒回應」。


//===== 每一件 a 物件的圖元順序 =====
//
//  ┌ 1. [PTP/Line 點位] 移到題目區 2 的該物件夾取點 (預教點位)
//  │
//  ├ 2. [SET 圖元] 關夾爪                 IO["EndModule"].DO[1] = 1
//  │    [Wait] 0.3 秒讓夾爪確實夾住
//  │
//  ├ 3. [PTP 點位] 移到【固定檢測位】
//  │    ※ 此點要讓物件完整入鏡且夠大 (面積要超過該顏色 profile 的 min_area)
//  │    ※ 教這個點位時, 樹莓派同時跑 io_test.py 看畫面, 直到出現綠框、左上角 seen= 顯示正確顏色
//  │
//  ├ 4. [SET 圖元] 拉高 ready             IO["ControlBox"].DO[0] = 1
//  │    → 樹莓派終端印「[a] 收到 ready, 投票 3 秒」
//  │
//  ├ 5. [WaitFor 圖元] 等 DI0 == 1        timeout 8000 ms (理由見上面「時序」)
//  │
//  ├ 6. [IF 圖元] DI0 == 1 的 7 秒窗內讀 DI1、DI2、DI3 → 三個顏色分支
//  │    (可用巢狀 IF: 先看 DI1, 再看 DI2, 再看 DI3)
//  │
//  ├ 6-1.[WaitFor 逾時的那條分支] 讀 DI1 DI2 DI3
//  │    == 1 1 1 → 辨識失敗: 建議把物件稍微轉個角度 / 重新對正鏡頭後, 回到第 4 步再試一次;
//  │               或直接放到暫置區跳過。
//  │    == 0 0 0 → 樹莓派沒有回應: 檢查 main_contest.py 是否還在跑、DO0 → GPIO26 接線。
//  │
//  ├ 7. [IF 圖元] 讀光電感測器那支 DI → 深度分支 (題目沒有深度判斷就省略本步)
//  │
//  ├ 8. [SET 圖元] 放下 ready             IO["ControlBox"].DO[0] = 0
//  │    ※ 不可省略: 樹莓派要看到 ready 回到 0 (WAIT_RELEASE 狀態) 才會接受下一件的觸發
//  │
//  ├ 9. [PTP/Line 點位] 依顏色 (和深度) → 移到題目區 3 對應點位
//  │
//  └ 10.[SET 圖元] 開夾爪                 IO["EndModule"].DO[1] = 0
//       [Line] 抬起離開
//
//  → 回到主流程, 接下一件 (下一件是 b 就插入 tm-flow-v1.txt 的 script 圖元)


//===== 整體 flow 範例 (假設題目要求 5 件: a, b, b, a, b) =====
//
//   Start
//    ├─ [起始姿態]  達明 J1~J6 = 0,0,90,0,90,0   (2025 題目卷評分規範)
//    ├─ [電爪開合一次]                            (評分規範要求)
//    ├─ 第 1 件 ── a 子流程 (上面 1~10 步的圖元)
//    ├─ 第 2 件 ── [Script] 插入 tm-flow-v1.txt
//    │              → script 送 GET, 樹莓派回 $x,y (手臂座標 mm; 不回顏色)
//    │              → script 移到上方、下降、夾取
//    │              → script 之後選手自己拉: 抬起 → 題目區 3 對應點位 → 開夾爪 → 抬起
//    │                放置點靠順序決定: 第 N 次 GET 一定是 PICK_ORDER 的第 N 個顏色
//    │                (樹莓派每收一次 GET 就前進一格, 找不到物件也前進), 所以每個 Script 圖元
//    │                後面直接接該顏色的放置點位即可
//    ├─ 第 3 件 ── [Script] 同上
//    ├─ 第 4 件 ── a 子流程
//    ├─ 第 5 件 ── [Script] 同上
//    └─ [回原點] 回起始姿態
//
//   b 通道的夾取順序寫在 main_contest.py 的 PICK_ORDER; 用完會回 $NONE。
//   a 與 b 的先後由本 flow 上圖元的排列決定。


//===== 賽前用 io_test.py 驗接線 (樹莓派端, 手臂不必先接好流程) =====
//   python3 io_test.py
//   1~9  送出 IO_CODES 裡第 1~9 個顏色的訊號 (預設 1=red 2=blue 3=green; 不看相機, 純測接線)
//   f    送出失敗碼 (R1 不拉高, R2 R3 R4 = 1 1 1)
//   0    全部繼電器關閉
//   r    把相機目前看到的顏色送出去 (和比賽動作一樣)
//   q    離開
//   畫面左上角: seen = 目前看到的顏色, ready = GPIO26 電位, last IO = 最後送出的訊號
//   啟動時終端會列出數字鍵對應表, 並提醒 IO_CODES 裡有哪些顏色在 vision_profiles.json 還沒存。


//===== 常見問題 =====
//
// Q: WaitFor DI0 一直等不到?
// A: 看樹莓派終端有沒有印「[a] 收到 ready」。
//    沒印 → DO0 到 GPIO26 的接線或電位有問題 (跑 io_test.py, 左上角 ready= 會即時顯示)。
//    有印但送了失敗碼 → 終端會印「沒看到任何 IO_CODES 裡的顏色」: 物件太小 (min_area)、
//    HSV 沒調好, 或顏色名和 IO_CODES 對不上。
//
// Q: 判到錯的顏色?
// A: 兩個顏色的 HSV 範圍重疊。用 vision_tuner.py 依現場燈光重調 (按 n 切換已存顏色),
//    再用 io_test.py 確認 seen= 顯示正確。
//
// Q: b 的 script 要改嗎?
// A: 不用。樹莓派回覆 $x,y, script 取 parts[0]、parts[1] 當手臂座標。
//    放置點不靠回覆內容, 靠 GET 的次數對 PICK_ORDER (見上面「整體 flow 範例」)。
//
// Q: 手臂逾時後讀到 DI 全是 0?
// A: WaitFor 的 timeout 設太長, 失敗碼已經收回。改成 8000 ms。
